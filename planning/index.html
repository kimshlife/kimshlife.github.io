SSketch · 문서와 코드가 같은 말을 하게

기획서, 패킷 명세, 실제 코드가 따로 움직이기 쉬운 6인 멀티플레이 프로젝트였습니다.

96 / 96EditMode 테스트 통과AI 도구로 작성한 테스트 클래스 6종

그림 파티 게임은 대부분 한 사람이 그리고 나머지가 맞히는 구조라, 맞히고 나면 그림의 역할이 끝납니다. SSketch는 낮에 그린 그림을 밤에 훔치고 아침에 익명으로 평가해, 그림이 끝까지 게임의 자원으로 남습니다.

  1. 문제

    기획서 · 패킷 명세 · 코드가 서로 다른 말을 하기 쉬운 구조

  2. 제약

    팀이 매일 작업을 마치고 Jira에 올리는 방식 — 자동 연동보다 수동 점검이 맞음

  3. 결정

    요구사항을 문서가 아니라 develop 코드 기준으로 다시 셈. 유명무실한 항목은 ‘제외’로 분모에서 뺌

  4. 문서

    요구사항 250건 · 12개 대분류 ID 체계, 설정 창 프로토타입·레드라인, 디자인 컨셉북 16쪽

  5. 결과

    진행률 62%(2026.09.26) · 담당 규칙 코드 테스트 96/96 · 특화 프로젝트 우수상

01요구사항을 코드 기준으로

기획서와 패킷 명세를 바탕으로 요구사항 250건을 12개 대분류 ID 체계(SYS · LOB · DRW · EVL 등)로 정리하고, 항목마다 우선순위와 담당을 붙였습니다. 8/31부터 9/26까지 develop 브랜치의 실제 코드를 보며 완료 · 부분 · 미착수를 반복해서 다시 판정했습니다.

확정 전 수치와 문서 간 충돌은 별도 시트에 모아, 결정할 것을 한곳에서 관리했습니다.

03소유권을 원장 하나로

씬 오브젝트 참조로 흩어져 있던 소유권을 정수 ID 기반 원장으로 옮기고, 창작자 · 운반자 · 마지막 확보 집 · 상태를 기록했습니다. 모든 상태 변경이 Commit 한 곳만 지나가게 해서, 서버 동기화를 붙일 때 그 지점 하나만 연결하면 되게 했습니다. 이 구조는 AI 코딩 도구로 구현했습니다.

04규칙에서 끌어낸 외주 사양

밤에는 익명화가 핵심이므로 같은 복장과 복면으로 실루엣을 통일하고 표정은 만들지 않기로 했습니다. 이 사양으로 제안서를 직접 작성해 외부 작업자와 캐릭터 7종의 커미션 계약을 진행하고, Unity 6 · URP 셰이더와 팔레트 UV 색 지정 규칙을 담은 전달 규격을 정리했습니다.

기여 경계 — 연막탄·섬광탄 구현, 전문가 리뷰 자료, 최종 영상·트레일러, 발표는 팀원 작업입니다.

SERVICE DESIGNRULE DESIGN

ProjectRG · 질문 수도 규칙으로 정한다

구매 이력과 장르 태그가 아니라, 사람의 플레이 성향을 기준으로 게임을 추천하는 플랫폼입니다.

5축성향 가중치전략 · 협동 · 창의 · 경쟁 · 탐험
12 + 3문항 구성기본 12 · 애매할 때만 보충 3
≤15 · <65보충 질문 발동1·2위 격차 또는 1위 점수

모두에게 15문항을 요구하면 이탈하고, 12문항으로 고정하면 경계선에 있는 사용자의 정확도가 떨어집니다. 결과가 애매할 때만 질문을 늘리는 규칙으로 둘을 함께 맞췄습니다.

  1. 문제

    같은 장르라도 플레이 스타일이 전혀 달라, 태그 기반 추천이 맞지 않는 게임을 권함

  2. 제약

    진단이 길면 이탈하고, 짧으면 경계선 사용자의 정확도가 떨어짐

  3. 결정

    선행 연구(Nick Yee · Bartle)를 5축으로 번역, 결과가 애매할 때만 보충 3문항

  4. 문서

    3유형 × 기본 12문항 진단 체계와 보충 질문 발동 기준

  5. 결과

    진단 → 결과 이미지 공유 → 성향별 게시판으로 이어지는 서비스 화면과 프론트엔드 구현 (일부 AI 코딩 도구 활용)

임의의 분류가 아니라 검증된 연구를 서비스 구조로 옮깁니다.

01문제 정의

게임 추천은 대체로 구매 이력과 장르 태그에 머뭅니다. 같은 공포 장르라도 전술을 짜는 사람과 부수는 사람, 협력하는 사람과 경쟁하는 사람이 한 태그 안에 섞여 있어, 맞지 않는 게임에 시간을 쓰고 원래 게임으로 돌아가는 순환이 반복됩니다.

02타깃

본인 성향을 파악하고 싶어 하는 층을 타깃으로 잡았습니다. 핵심 수요는 ‘실패 없는 게임 선택’ — 시간과 비용을 낭비하지 않으려는 동기입니다.

기여 경계 — LLM 응답 안정화와 벡터 DB 확장은 백엔드 담당이 주도한 영역이라 본인 성과로 쓰지 않았습니다.

GAME DESIGNBALANCE

NeonTetrisWars · 표준은 가져오고, 밸런스는 직접 정한다

웹 테트리스의 둔한 조작과 불완전한 규칙이 몰입을 가장 크게 깨뜨린다고 봤습니다.

표준 그대로직접 설계
7-Bag 알고리즘회전 제한 15회
SRS 회전 규칙락 딜레이 게이지
고스트 블록 · 홀드키보드만으로 메뉴 조작

제한이 없으면 무한 회전으로 게임이 멈추고, 너무 빡빡하면 T-Spin 같은 고난도 기술이 막힙니다. 두 조건을 동시에 만족하는 지점이 15회였습니다.

  1. 문제

    둔한 조작감 · 불완전한 규칙 · 탭 전환이나 이탈로 끊기는 세션

  2. 제약

    검증된 규칙을 새로 만들 이유는 없지만, 밸런스 값을 남의 기준에 맡기면 기획을 포기하는 것

  3. 결정

    표준(7-Bag · SRS)은 그대로, 회전 제한과 락 딜레이 시각화는 직접 설계

  4. 문서

    업데이트 로그에 규칙 변경 이력을 날짜별로 기록 — 백투백, NEXT 1→3개, 버퍼 행

  5. 결과
